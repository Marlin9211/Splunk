The mental model you need before starting

Lookup side: add meaning to data

Start with an indexed event. An event may contain a value such as productId=FS-25-001 or status=404 that is technically useful but not very descriptive.

Find the shared field. A lookup table contains a corresponding field. That paired field is what allows Splunk to connect the event to the correct lookup row.

Know the supporting pieces. The lookup table stores reference data; the lookup definition tells Splunk which lookup to use; the lookup command enriches events; inputlookup reads lookup contents; outputlookup writes search results to a supported lookup destination; an automatic lookup applies enrichment at search time without manually invoking lookup.

Alert side: turn results into action

Start with the search. The search defines what Splunk is monitoring.

Choose when it runs. Scheduled alerts run at defined times. Real-time alerts search continuously.

Define when results matter. Trigger conditions decide when search results become an alert. Throttling controls repeated triggering for a configured period.

Define what happens next. Alert actions determine the response after a trigger. When Add to Triggered Alerts is enabled, a qualifying trigger can create a record on the Triggered Alerts page.

Three distinctions that prevent common confusion

Do not confuseKey distinction to remember
lookup vs. inputlookup vs. outputlookuplookup enriches events; inputlookup reads the lookup table into the search; outputlookup writes search-result fields to a supported lookup destination.
Scheduled report vs. scheduled alertA scheduled report performs its action every time it completes. A scheduled alert performs its action only when its trigger condition is satisfied.
Alert definition vs. triggered alert instanceThe definition contains the alert configuration. Triggered Alerts contains records of qualifying alert instances when the required action and retention conditions are met.

Translator phase · Understand

Move from recognizing features to explaining what they mean.

In the Reporter phase, you identified the building blocks: lookup types and commands, alert timing, trigger conditions, throttling, and alert actions. The Translator phase changes the question. Instead of asking “What is this?”, you will ask “What does this configuration cause Splunk to do, and what does the analyst learn from the result?”

Your goal: build a mental model of how data moves from a raw event to useful context, how a saved search becomes monitoring logic, and how a triggered alert becomes an investigation record.

Use this mental model

RAW EVENT → ADD CONTEXT → MONITOR CONDITION → TRIGGER → INVESTIGATE RECORD

A lookup can make an event easier to understand. An alert can repeatedly evaluate search results. When its trigger condition is satisfied, an action can create a record analysts can investigate.

1 · Translate lookup enrichment

A raw event may contain a value such as productId=FS-25-001. That value is useful to Splunk, but it may not tell an analyst much by itself. A lookup uses a shared field to match the event to an external record and return additional fields such as a product name or price.

Think: What field connects the event to the lookup? What new context appears after the match? The original event is being enriched, not replaced.

2 · Translate alert behavior

An alert starts with a saved search, but the search alone does not explain the monitoring behavior. You must also interpret when the search runs, what result causes a trigger, and what action occurs after the trigger.

Think: Scheduled or real-time? One qualifying result or a pattern of results? What exact condition must become true before Splunk acts?

3 · Translate throttling

Throttling does not stop Splunk from searching. It suppresses repeated alert triggers for a configured period so the same condition does not continually create duplicate alert activity.

Think: The condition can still exist while another notification or alert action is temporarily suppressed.

4 · Translate Triggered Alerts

An alert definition describes monitoring logic. A triggered alert instance is evidence that the configured trigger condition was actually satisfied. If Add to Triggered Alerts is enabled, that instance can remain visible until its retention expires or the listing is removed.

Think: Definition = what Splunk should watch for. Triggered instance = evidence that the condition occurred.

How to approach the next activities

Do not hunt for matching vocabulary. Read each situation as a short cause-and-effect story. Identify the input, determine what Splunk does with it, then explain the result the analyst sees.

Keep these relationships in view: event field ↔ lookup field · saved search ↔ alert type · results ↔ trigger condition · trigger ↔ action · throttle ↔ suppression window · expiration ↔ visibility on Triggered Alerts.

Lesson 200.7 — Creating and Using Lookups

Use these expandable study records as the authoritative lesson map. They preserve the source lesson's scope while converting it into retrieval and comprehension prompts.

7.1 Describe Lookups
  • Machine data may contain valuable information that is incomplete or difficult for humans to understand. Splunk lookups enrich or transform data by referencing external tables or files.
  • Lookups add field-value combinations from lookup tables external to available indexes. Matching is based on paired fields: at least one field exists in both indexed events and the lookup table.
  • Product example: productId exists in the web index and in products.csv. A match can add information such as product_name and price to search results.
  • Four lookup types: CSV (static; small, relatively static data), External (scripted; Python/binary against a source such as DNS), KV Store (large or frequently updated collections), and Geospatial (KML/KMZ; coordinates to geographic features; choropleth maps).
  • Lookup table files contain lookup tables. A standard lookup pulls fields from a table when corresponding fields match events. CSV and geospatial lookups require uploaded lookup table files. One lookup table file can support multiple lookup definitions.
  • A lookup definition supplies a lookup name and path to the lookup table and may contain matching rules or field restrictions. All lookup types require a definition; one table can have multiple definitions.
  • Automatic lookups apply a lookup to all searches at search time, removing the need to manually invoke lookup.
  • lookup adds fields to events in search results; inputlookup searches lookup-table contents; outputlookup writes result fields to a static lookup table or KV Store collection. outputlookup cannot be used with external lookups.
7.2 Examine a Lookup File Example
  • CSV lookups are file-based lookups that match event field values to values in a static CSV table and output corresponding fields. They are best for small data sets.
  • A CSV is a plain-text tabular format. Each line represents a row and values are separated by commas or another specified delimiter. It is both human-readable and machine-readable.
  • CSV lookup restrictions: at least two columns; one column must contain values corresponding to a field in events; characters must be plain ASCII/valid UTF-8; non-UTF-8 is unsupported; \r line endings from OS X 9 or earlier are unsupported; header rows cannot exceed 4096 characters.
  • Splunk Web path: Settings → Lookups → Lookup table files. The page lists Path, Owner, App, Sharing, and Status. Appropriate roles can upload files, manage permissions, move, and delete tables.
  • Use | inputlookup products.csv to inspect a lookup. A subsearch can locate information for a particular productId. Results can also be piped to where; the lesson example filters products whose listed price and sale price differ by more than $5.
7.3 Create a Lookup File and Lookup Definition
  • The lesson's CSV example enriches web access events with status_description and status_type, helping users understand or search HTTP status codes.
  • HTTP code categories identified by the source: informational responses, successful responses, redirection messages, client error responses, and server error responses.
  • Upload workflow: extract the downloaded CSV; from Search select Settings → Lookups; choose + Add new for Lookup table files; choose search as destination app; browse to the CSV; use http_codes.csv as Destination filename; Save. The role needs the upload_lookup_files capability.
  • File permissions: locate http_codes.csv → Permissions → This app only (search) → grant Everyone Read → Save.
  • Create definition: Settings → Lookups → + Add new under Lookup definitions; destination app search; name http_codes; Type File-based; Lookup file http_codes.csv; Save.
7.4 Use the Lookup in Searches
  • Using the lookup adds fields from the table to search results. The shared status field is used with the OUTPUT modifier to add status_description and status_type; the new fields can appear in the Fields sidebar.
  • Scenario: an admin wants the total web requests by HTTP status meaning over 24 hours—successful requests, server errors, client errors, and the errors themselves.
  • Without the lookup, the web index provides status codes with no easy human-readable interpretation. With the lookup, additional fields enrich the results and make the status categories/errors understandable.
7.5 Configure an Automatic Lookup
  • Manual lookups are invoked with lookup; automatic lookups apply to all searches at search time.
  • Settings → Lookups → + Add new for Automatic lookups; destination app search; name http_codes; lookup table http_codes; apply to sourcetype access_combined.
  • Input mapping: CSV status on the left, event status on the right. Output fields: status_description and status_type, with CSV column names on the left and event fields on the right. Save.
  • The Automatic lookups page exposes information and editing options including Permissions, Clone, Move, and Delete. Set permissions to This app only (search), Everyone Read, then Save.
  • Verification: return to Search & Reporting and search the data. Splunk can now retrieve status_type and status_description without the admin explicitly using the lookup command.

Lesson 200.8 — Creating Scheduled Reports and Alerts

8.3 Describe Alerts
  • Alerts support proactive monitoring and timely response. They use a saved search in real time or on a schedule, trigger when results meet conditions, and can initialize alert actions.
  • Workflow: Search (what to track) → Alert type (how often the search runs) → Trigger conditions and throttling (when/how often to trigger) → Alert action (what happens after triggering).
  • Two alert types: scheduled and real-time. Definitions are based on alert-search timing; timing, triggering, and other behaviors can be configured for the scenario.
8.4 Scheduled Alert — Sales Scenario
  • Scheduled alerts search regularly and are appropriate when immediate monitoring is not the priority. Scenario: daily goal 800 sales; search each day at 23:00; trigger if results are below 800.
  • The search counts events containing purchase in the action field; then use Save As → Alert.
  • Settings: Title Sales_Alert_Less_than_800_items; Description optional; Permissions Shared in App; Alert type Scheduled; every day at 23:00; Expires 24 hours. Expires controls the lifespan of records on Triggered Alerts.
  • Trigger Conditions: Number of Results less than 800; Trigger Once/For each result as presented in the source; Throttle unchecked. Throttle suppresses subsequent alerts for a specified period but is not used here.
  • Trigger Action: Add to Triggered Alerts; Severity Medium; Save. One or more actions can be added. Severity is a tag used to filter/locate alerts on Triggered Alerts.
  • After save, permissions can be edited, the alert can continue to be edited, or View Alert can be selected. The alert view supports reviewing/editing settings.
  • Scheduled report distinction: a scheduled report runs its action every time the report completes; a scheduled alert runs its action only when triggered by search results.
8.4 Real-Time Per-Result Alert — Web Server Errors
  • Real-time alerts search continuously and are useful when immediate monitoring/response matters. They can trigger once per result or when conditions occur within a rolling time window.
  • Per-result scenario: monitor www1, www2, and www3 for HTTP server error responses (500–599). A server problem can generate an alert for every request, so throttling is used to prevent a flood.
  • Search the web index for status >= 500 on the three servers and save as Alert.
  • Settings: Title NOC_Alert_Web_Server_Errors; Description optional; Permissions Private; Alert type Real-time; Expires 24 hours.
  • Trigger: Per-Result; Throttle checked; suppress results containing field values 500–511; suppress triggering for 60 minutes. The source explains that this permits only one alert during the one-hour window for each status value in that range.
  • Action: Add to Triggered Alerts; Severity High; Save. The source notes that email could also be appropriate in a real-world scenario.
8.4 Rolling Window Alert — Failed Logins
  • A rolling-window alert is a real-time alert in which a specific time window is part of the event pattern.
  • Scenario: notify when there are more than 20 failed login attempts within five minutes. Search the security index for Failed and password, then save as Alert.
  • Settings: Title SEC_Alert_20_failed_login; Description optional; Permissions Private; Alert type Real-time; Expires 24 hours.
  • Trigger Conditions: Number of Results greater than 20 in 5 minutes; Trigger Once/For each result as shown by the source; Throttle checked; suppress triggering for 30 minutes.
  • Action: Add to Triggered Alerts; Severity High; Save.
8.4 View and Manage Alerts
  • The Alerts page lists all alerts for an app and is available from the app's top-level navigation. Expanding an alert entry exposes editing options; the lesson directs learners to use a live Splunk environment to explore all available options.
8.5 View Triggered Alerts
  • Recently triggered alert records are available from Triggered Alerts or an Alert Details page. Triggered Alerts shows instances, with records available for 24 hours by default.
  • Access: Activity → Triggered Alerts.
  • An alert instance appears when Add to Triggered Alerts is enabled, the alert triggered recently, retention is not complete, and the listing has not been deleted. Expiration can be configured per alert—for example, seven days instead of 24 hours.
  • Visibility can be changed by updating expiration, deleting a listing, or disabling an alert to prevent future triggering.
  • Selecting View results for NOC_Alert_Web_Server_Errors opens the triggering event in Search & Reporting. It is a troubleshooting starting point and can expose source IP, server action, host name, HTTP version, HTTP error code, and other event data.
  • Lesson summary also notes possible actions such as sending email notifications, executing scripts, or adding the alert to the triggered-alert list.
